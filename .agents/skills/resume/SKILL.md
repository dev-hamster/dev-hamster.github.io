## 대상 파일

- `src/constants/resume.ts` — 이력서 데이터 (WORK_EXPERIENCE, PROJECT, EDUCATION 등)
- `src/types/resume.ts` — 타입 정의
- `src/pages/resume.tsx` — 렌더링 페이지

## 리뷰 원칙

1. 각 프로젝트의 description을 **PAAR 구조**로 점검한다.
2. 모호한 표현("개선했습니다", "기여했습니다")은 **수치 기반 성과**로 대체한다.
3. 감성적·추상적 문구는 제거하고, 사실과 근거만 남긴다.
4. 한 문장에 하나의 메시지만 담는다. 복합 문장은 분리한다.

## PAAR 프레임워크

각 프로젝트의 description 항목이 아래 4가지를 충족하는지 점검한다.

| 단계 | 질문 | 체크 포인트 |
|------|------|------------|
| **P**roblem | 왜 이 문제가 중요했는가? | 비즈니스 임팩트, 사용자 영향, 긴급도가 드러나는가 |
| **A**nalyze | 어떤 선택지를 검토했고 왜 그 방법을 택했는가? | 대안 비교, 기술 선택 근거, 제약 조건이 명시되어 있는가 |
| **A**ction | 구체적으로 무엇을 어떻게 했는가? | 본인의 역할, 사용 기술, 트레이드오프 관리가 명확한가 |
| **R**esult | 어떤 지표로 검증했는가? | 정량 수치(시간, %, 건수), before→after 비교가 있는가 |

> 모든 항목이 4단계를 다 갖출 필요는 없다. 단, Result는 반드시 포함해야 한다.

## 피드백 형식

리뷰 결과는 프로젝트 단위로 아래 형식을 따른다:

```
### [프로젝트명]

**현재**: (기존 description 인용)
**문제**: (PAAR 중 빠진 요소 또는 모호한 표현 지적)
**제안**: (구체적 수정안)
```

## 추가 체크리스트

- [ ] description 첫 문장이 성과(Result)로 시작하는가 (성과 → 맥락 → 방법 순서)
- [ ] 기술 스택이 언급될 때 "왜 그 기술인지" 근거가 있는가
- [ ] 동일한 표현이 여러 프로젝트에서 반복되지 않는가
- [ ] `<span class="highlight">` 태그가 핵심 성과에만 사용되었는가
