<ThreadItem>
  탐테는 어떻게 하는거지? <br />- 간섭받지않고 오로지 테스트에 집중 <br /> -
  개개인의 자유 의지와 책임감이 중요

<ThreadItem>
  가장 중요한 것은 테스트 설계와 수행을 동시에 하는 것임! 이것을 하려면 이전에
  테스트를 통해 **학습** 한 것을 활용함
</ThreadItem>

<ThreadItem>세션 시간을 정해놓고 **테스트 차터**로 진행함</ThreadItem>

<ThreadItem>
  테스트 차터는 대게 테스트 목적, 자원, 찾아야 하는 정보로 구성되지만 양식이
  어렵다면 간략하게 목적을 쓰는 것도 좋음! 예를 들어서 '사용자가 구매를 완료하지
  못하는 시나리오를 찾아라' 같은 것도 좋은 차터가 될 수 있음
</ThreadItem>

<ThreadItem>
  좋은차터란? 동작을 구체적으로 명시하지 않으면서 테스트가 나아가야할 방향을
  작성한 것
</ThreadItem>

  <ThreadItem>
  ```tsx
  // ❌ Don’t 
‘보안에 취약한 모든 부분을 찾기 …(생략) 탐험을 떠나자’ // 너무 광범위함
‘john doe를 가지는 이름을 제대로 처리하는지 …(생략) 탐험을 떠나자’ // 너무 구체적임
````
  ```tsx
  // ✅ Do
  // 여러 차터로 세밀하게 나누기
  ‘보안에 취약한 점을 찾기 위해서 …(생략) 탐험을 떠나자’
  ‘사용자가 구매하지 않을 콘텐츠에 접근할 수 있는지 …(생략) 탐험을 떠나자’
````

훌륭한 차터는 아주 명확한 행동 지침이나 결과물에 대한 언급 없어도 영감의 원천이 된다.

</ThreadItem>

<ThreadItem>
  차터 작성하는 방법! <br /> 1. 요구사항 회의 도중에 발견되는 사항. 예를들어
  개발자 얘기하면서 탐색해야할 곳을 발견하거나, 숨겨진 요구사항(신뢰성,
  규모가변성 등)들을 차터로 만들자 <br /> 2. 새로운 기능과 연동이 잘 되는지,
  변경된 조건에도 잘 동작하는지, 미래에 발생할 위험 요소(해킹 등)에 대해 차터를
  만들자 <br />
  3. 현재 집중하고 있는 차터에서 다른 방향으로 탐색하고 싶은 유혹이 들 때
</ThreadItem>

관찰하는건 어려운 일임

- 기대한 결과대로 동작한다해도, 확인하지 못했던 부분에서 치명적인 것이 있을 수도 있음
- 무주의 맹시
- 의도적으로 그 상황들을 찾아내야 함

본질적인 질문을 던져야함
BAD: 로그인을 하고 '환영합니다!' 메세지가 보여줌
GOOD: 로그인 후에 접근 권한이 있는 정보를 열람할 수 있음

숨겨진 변수를 찾는 팁

1. 셀 수 있는 것들

- 0, 1 다수 휴리스틱: 결과값으로 0개, 1개, 1개 이상을 가지는 경우를 만들어 테스트하기
- 극대 휴리스틱: 처리할 수 있는 값보다 더 많은 입력값이나 요청으로 테스트
- 극소수 휴리스틱: 소프트웨어가 기대하는 값보다 더 작은 수로 입력하거나 더 적은 요청으로 테스트

0, 1, 다수 휴리스틱인 경우 검색 데이터개 0개인 경우 적절한 ui를 보여주는게 떠오름
극대휴리스틱인 경우 흔히 '따닥'이라 불리는 연속 요청이 떠오름

타협하지 않고 꼭 지켜야할 규칙들을 찾아내기

1. 항상 올바르게 동작해야 하는 핵심 기능
2. 꼭 지원해야 하는 것들: 신뢰성, 규모 가변성, 사용성, 정확성 같은 품질 기준
3. 프로젝트 이해관계자들이 주목하고 있는 다른 위험 요소들
